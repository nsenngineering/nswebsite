## Part 1 — `nswebsite` repo

### Change 1.1 — `deploy-dev.yml`: Build Uses Placeholder for R2 URL

**File**: `.github/workflows/deploy-dev.yml`  
**Lines changed**: workflow-level `env` block + build job `env` block + three new deploy steps

#### What was wrong

The entire site is built once, and that same compiled artifact is deployed to dev, stage, and production. Next.js bakes `NEXT_PUBLIC_*` environment variables into the compiled HTML and JavaScript files at build time — they become hardcoded string literals in the output.

The build job runs inside the GitHub `dev` environment, so it picks up `NEXT_PUBLIC_R2_BASE_URL` from the `dev` environment secrets. The resulting artifact contains every image URL pointing to the dev R2 bucket (`pub-f58468244b5b418fbb2205a1c42100fd.r2.dev`).

When this same artifact is then promoted and deployed to staging and production, the HTML files still contain the dev R2 bucket URL. Every image on the production website — hero photos, project galleries, team photos, the logo used as the favicon — loads from the **dev bucket**, not the prod bucket. Similarly, the Turnstile site key baked in is always the dev key regardless of which environment the user is actually visiting.

This creates two problems:
1. **Reliability**: if the dev R2 bucket is ever modified, cleared, or has its access changed, production images break.
2. **Correctness**: Turnstile analytics and bot detection thresholds are per-site-key, so production traffic was being counted against the dev Turnstile application.

#### What the fix does

The build step now compiles with **placeholder strings** instead of real values:

```yaml
NEXT_PUBLIC_R2_BASE_URL: "https://NSENGINEERING_R2_URL"
NEXT_PUBLIC_TURNSTILE_SITE_KEY: "NSENGINEERING_TURNSTILE_KEY"
```

These placeholder strings end up as literal text inside the compiled HTML and JS files in the `out/` directory. Before each environment's wrangler deploy runs, a new **"Inject `<env>` R2 URL and Turnstile key"** step runs a `find+sed` pass over every `.html` and `.js` file in `out/`:

```bash
find ./out -type f \( -name "*.html" -o -name "*.js" \) \
  -exec sed -i "s|https://NSENGINEERING_R2_URL|${R2_URL}|g" {} \;
find ./out -type f \( -name "*.html" -o -name "*.js" \) \
  -exec sed -i "s|NSENGINEERING_TURNSTILE_KEY|${TURNSTILE_KEY}|g" {} \;
```

Each deploy job (`deploy-dev`, `deploy-stage`, `deploy-prod`) runs inside its own GitHub environment, so `secrets.NEXT_PUBLIC_R2_BASE_URL` resolves to the correct bucket URL for that environment:
- `deploy-dev` (GitHub env: `dev`) → `pub-f58468244b5b418fbb2205a1c42100fd.r2.dev`
- `deploy-stage` (GitHub env: `staging`) → `pub-43efaf62899f4c4d94f31b2830227f25.r2.dev`
- `deploy-prod` (GitHub env: `production`) → `pub-f5c1196e75664b0a8d9ba70c46527044.r2.dev`

The artifact file downloaded for each deploy job is a fresh copy (GitHub Actions artifact), so modifying it in one job does not affect the other jobs.

#### How to verify

After running the pipeline, inspect the HTML source of any page on each environment. The image URLs should reference that environment's R2 domain:
- `dev.nsengineering.com.np` → `pub-f584...r2.dev/...`
- `stage.nsengineering.com.np` → `pub-43ef...r2.dev/...`
- `nsengineering.com.np` → `pub-f5c1...r2.dev/...`

Also check that the string `NSENGINEERING_R2_URL` does **not** appear anywhere on the deployed pages (would indicate the substitution failed).

#### Prerequisite

Add `NEXT_PUBLIC_TURNSTILE_SITE_KEY` to the **`staging`** GitHub environment secrets. The inject step has a `:?` guard that will fail the pipeline with a descriptive error if either secret is empty.

## Part 2 — `email-worker` repo

### Change 2.1 — `wrangler.toml`: Deleted

**File**: `wrangler.toml` (deleted)

#### What was wrong

Two wrangler configuration files existed side by side: `wrangler.toml` and `wrangler.jsonc`. When both exist, wrangler 3+ gives precedence to `wrangler.jsonc`. The `wrangler.toml` file had three problems:

1. **Missing production environment**: It only defined `[env.dev]` and `[env.staging]`. If someone ran `wrangler deploy --env production` locally without knowing wrangler.jsonc takes precedence, the command would fail silently or deploy the wrong thing.

2. **Stale routes that could intercept page requests**: It contained:
   ```toml
   [env.dev]
   route = "dev.nsengineering.com.np/*"
   
   [env.staging]
   route = "stage.nsengineering.com.np/*"
   ```
   These routes, if ever activated, would route **every request** to those domains — including page loads for the Cloudflare Pages site — through the email worker. This would break the entire website. They were dormant only because wrangler.jsonc (which has no routes) took precedence.

3. **False authority**: Having two config files made it unclear which one was authoritative. Any developer maintaining the project would need to know the precedence rule.

#### What the fix does

`wrangler.toml` is deleted. `wrangler.jsonc` is the single source of truth for all three environments.

#### How to verify

`ls /home/shotripathi/email-worker/wrangler*` — should only show `wrangler.jsonc`. Running `wrangler deploy --env production` should succeed without errors.

### Change 2.2 — `wrangler.jsonc`: Remove Hardcoded Email Addresses

**File**: `wrangler.jsonc`

#### What was wrong

All three environments had `"QUOTATION_EMAIL": "kunwarritika46@gmail.com"` hardcoded in the `vars` section. This meant:
- Every form submission from dev, staging, and production went to the same personal Gmail inbox
- There was no way to distinguish test submissions from real ones
- The email address was committed in plaintext in a version-controlled file
- `CAREERS_EMAIL` and `SUPPORT_EMAIL` were never set at all (not in vars, not set as secrets)

The `vars` section in wrangler config is for non-sensitive, per-environment configuration that is acceptable to commit. Email recipient addresses are sensitive operational configuration that should be controlled per-environment and not committed to source code.

#### What the fix does

The `vars` section now only contains `ENVIRONMENT` (a non-sensitive value that controls which sender domain to use). All five operational values (`QUOTATION_EMAIL`, `CAREERS_EMAIL`, `SUPPORT_EMAIL`, `RESEND_API_KEY`, `TURNSTILE_SECRET_KEY`) are removed from vars and are now exclusively set as Worker secrets by the CI pipeline (see Change 2.3).

The config also gains explanatory comments making it clear which values are expected as secrets and why they are not in the config file.

### Change 2.3 — `deploy-dev.yml`: Secrets Pipeline Rewrite

**File**: `.github/workflows/deploy-dev.yml`

#### What was wrong

**This is the most critical fix in the email-worker repo.**

The original workflow passed secrets to `wrangler deploy` as GitHub Actions environment variables:

```yaml
- name: Deploy Cloudflare Worker (Prod)
  run: wrangler deploy --env production
  env:
    RESEND_API_KEY: ${{ secrets.RESEND_API_KEY_PROD }}
    TURNSTILE_SECRET_KEY: ${{ secrets.TURNSTILE_SECRET_KEY_PROD }}
    QUOTATION_EMAIL: ${{ secrets.QUOTATION_EMAIL_PROD }}
    CAREERS_EMAIL: ${{ secrets.CAREERS_EMAIL_PROD }}
    SUPPORT_EMAIL: ${{ secrets.SUPPORT_EMAIL_PROD }}
```

**`wrangler deploy` does not read GitHub Actions env vars as Worker secrets.** It reads `wrangler.toml`/`wrangler.jsonc` only. These five env vars were completely ignored. The entire block was decorative.

The consequences of this:
- `QUOTATION_EMAIL`, `CAREERS_EMAIL`, and `SUPPORT_EMAIL` were never deployed to any worker as secrets. They only existed in `vars` (hardcoded to the same Gmail address for all environments, see Change 2.2).
- `RESEND_API_KEY` and `TURNSTILE_SECRET_KEY` existed on the workers only because they were set manually at some point via `wrangler secret put`.
- On `email-worker-prod`, whoever manually ran `wrangler secret put` used the name `TURNSTILE_SECRET_KEY_PROD` instead of `TURNSTILE_SECRET_KEY`. The code reads `env.TURNSTILE_SECRET_KEY`, so it was `undefined` in production. The Turnstile siteverify API received `secret=undefined`, returned `success: false`, and **every form submission on production was rejected with "Security verification failed"**.

Additionally:
- The workflow trigger was `feature/ritika/email` — a feature branch. After this branch is merged to master, no CI push trigger would ever fire again.
- `npm install -g wrangler` installs whatever the latest version is at runtime, which is non-deterministic.

#### What the fix does

Each deploy job is restructured into two explicit steps:

**Step 1 — Deploy code**: `wrangler deploy --env <env>` deploys the worker script and the non-sensitive `vars` from `wrangler.jsonc`.

**Step 2 — Set secrets**: For each of the five secrets, `printf '%s' "$VALUE" | wrangler secret put SECRET_NAME --name worker-name` is called explicitly. `printf '%s'` is used instead of `echo` to avoid adding a trailing newline to the secret value.

Each secret has a `:?` guard that fails fast with a descriptive error message if the secret is not set in the GitHub environment, making misconfiguration immediately visible.

Example for production:
```bash
printf '%s' "$RESEND_API_KEY"       | wrangler secret put RESEND_API_KEY       --name email-worker-prod
printf '%s' "$TURNSTILE_SECRET_KEY" | wrangler secret put TURNSTILE_SECRET_KEY --name email-worker-prod
printf '%s' "$QUOTATION_EMAIL"      | wrangler secret put QUOTATION_EMAIL      --name email-worker-prod
printf '%s' "$CAREERS_EMAIL"        | wrangler secret put CAREERS_EMAIL        --name email-worker-prod
printf '%s' "$SUPPORT_EMAIL"        | wrangler secret put SUPPORT_EMAIL        --name email-worker-prod
```

The workflow trigger is updated from `feature/ritika/email` to `master`. `workflow_dispatch` is retained for manual runs.

#### What still needs to be done manually

The **live** `email-worker-prod` still has the wrong secret name. Before the next pipeline run, fix it manually:
```bash
wrangler secret put TURNSTILE_SECRET_KEY --name email-worker-prod
# paste the prod Turnstile secret key when prompted
```
Then in the Cloudflare dashboard → Workers → `email-worker-prod` → Settings → Variables → delete `TURNSTILE_SECRET_KEY_PROD`.

After the next successful pipeline run, all secrets will be correctly named and the manual state won't matter.

### Change 2.4 — `src/index.js`: CORS Pattern Match for Preview URLs

**File**: `src/index.js`

#### What was wrong

The CORS check used an exact-match array lookup:
```javascript
const isAllowed = CONFIG.allowedOrigins.includes(origin);
```

The `allowedOrigins` array only contained the four production custom domains. When a developer or QA engineer tested a form on a Cloudflare Pages preview URL (e.g., `https://598146ed.nsengineering-stage.pages.dev`), the browser sent an `Origin` header that didn't match any entry in the array. The worker returned restrictive CORS headers with `Access-Control-Allow-Origin: https://nsengineering.com.np` (the first entry), which caused the browser to block the form submission with a CORS error.

This made it impossible to test form functionality on preview deployments without deploying to a custom domain first — defeating much of the purpose of having preview deployments.

#### What the fix does

A new `isAllowedOrigin()` method on `CONFIG` checks both the exact-match list and a regex pattern:

```javascript
isAllowedOrigin(origin) {
  if (!origin) return false;
  if (this.allowedOrigins.includes(origin)) return true;
  return /^https:\/\/[a-z0-9-]+\.(nsengineering-dev|nsengineering-stage|nsengineering-prod)\.pages\.dev$/.test(origin);
},
```

The regex matches:
- `https://<deployment-id>.nsengineering-stage.pages.dev` — unique deployment preview URLs
- `https://stage.nsengineering-stage.pages.dev` — branch alias URLs (format: `<branch>.<project>.pages.dev`)

The pattern is intentionally scoped to the three known CF Pages project names — it does not allow arbitrary `*.pages.dev` origins.

`getCorsHeaders()` is updated to call `CONFIG.isAllowedOrigin(origin)` instead of `CONFIG.allowedOrigins.includes(origin)`.

### Change 2.5 — `src/index.js`: Remove Debug Log from Production

**File**: `src/index.js`, line 187 (original)

#### What was wrong

```javascript
const data = await response.json();
console.log("TURNSTILE VERIFY RESPONSE:", data);
return data;
```

`console.log` in a Cloudflare Worker writes to the Worker's real-time log stream (visible in the CF dashboard and via `wrangler tail`). The full Turnstile verification response object was being logged on every form submission in every environment, including production. This response includes the `hostname` the challenge was issued for, `error-codes`, and other metadata — unnecessary information disclosure to anyone with access to the Worker logs.

#### What the fix does

The three lines are collapsed into one:
```javascript
return await response.json();
```

### Change 2.6 — `src/index.js`: Remove `error.message` from 500 Responses

**File**: `src/index.js`, catch block

#### What was wrong

```javascript
return new Response(
  JSON.stringify({
    success: false,
    error: 'Internal server error',
    details: error.message,   // ← exposed to the browser
  }),
```

`error.message` in a JavaScript runtime error often contains internal implementation details: stack traces, variable names, API endpoint paths, library version strings. Sending this to the browser in an API response leaks the internal workings of the worker to any client — including malicious ones probing for information.

#### What the fix does

```javascript
return new Response(
  JSON.stringify({ success: false, error: 'Internal server error' }),
```

The error is still logged server-side via `console.error('Worker error:', error)` (which goes to the Worker logs, not the browser), so debugging remains possible without exposing internals.

### Change 2.7 — `package.json`: Remove `@marsidev/react-turnstile`

**File**: `package.json`

#### What was wrong

```json
"dependencies": {
  "@marsidev/react-turnstile": "^1.5.2"
}
```

`@marsidev/react-turnstile` is a React component library for rendering the Turnstile widget in a browser. Cloudflare Workers run in a V8 isolate — there is no DOM, no React, no browser APIs. This package cannot be imported or used in the Worker. It was never imported anywhere in `src/`. Its presence:
- Added unnecessary weight to the `node_modules` directory
- Could confuse future developers into thinking it was used or needed
- Would be bundled into the Worker output by wrangler if ever accidentally imported

#### What the fix does

The `dependencies` field is cleared. The actual Turnstile implementation in the worker uses the `fetch` API to call the Cloudflare siteverify endpoint directly — no library needed.

### Change 2.8 — `test/index.spec.js`: Replace Stub Tests

**File**: `test/index.spec.js`

#### What was wrong

The tests were the default Cloudflare Workers project template:
```javascript
expect(await response.text()).toMatchInlineSnapshot(`"Hello World!"`)
```

The worker never returns "Hello World!" — these tests would fail immediately if run. Having tests that don't pass provides false confidence in CI and makes it impossible to catch regressions.

#### What the fix does

The test file is replaced with five test suites that actually test the worker's behaviour:

**CORS** — three tests:
- `OPTIONS` from an allowed origin (`https://nsengineering.com.np`) → 204 with correct `Access-Control-Allow-Origin` header echoing the request origin
- `OPTIONS` from a Pages preview URL (`https://abc123.nsengineering-stage.pages.dev`) → 204 with the preview URL echoed back (confirms Change 2.4 works)
- `OPTIONS` from an unknown origin (`https://evil.com`) → the response `Access-Control-Allow-Origin` header is locked to the first allowed origin, not the request origin

**Method handling** — two tests:
- `GET` → 405
- `PUT` → 405

**Turnstile enforcement** — one test:
- `POST` with a valid JSON body but no `turnstileToken` → 400 with `success: false` and an error message containing "Security verification"

**Email type routing** — one test:
- `POST` with an unknown `emailType` — confirms the routing code path is reachable and returns 400 regardless (either Turnstile fails or the unknown-type branch fires)

**Error response shape** — one test:
- `POST` with invalid JSON (parse error) → 500, `success: false`, and **no `details` field** (confirms Change 2.6 is in effect)
